# Delta broker capability completion report

**Status:** Concrete Delta India REST-backed wrapper methods, denomination-aware planning, multicoin runtime wiring, documentation, and offline request/response tests have been added locally for draft PR #96. Changes have not been merged. No private exchange call, credential use, testnet/live order, deployment, or bot launch occurred. This work is not live-readiness approval.

## Completed implementation

- `delta_api_wrapper.py` now provides concrete methods rather than missing-interface stubs:
  - Complete bounded cursor pagination for the public product catalogue and private order listings. Delta `meta.after = null` is recognized as terminal; missing cursors on full pages, repeated cursors, malformed pages, and page-limit overflow fail closed. Execution metadata lookup requires one exact symbol from a complete catalogue (not the legacy one-page USDT/USD alias lookup).
  - Exact-asset available wallet balance selection; duplicate, absent, malformed, zero/negative, or non-finite balances are unavailable. `get_available_balance_usdt()` only reads an actual USDT row and never substitutes USD, INR, or another collateral asset.
  - Delta L2 executable top-of-book parsing with exact symbol/product membership, exchange timestamp freshness/future checks, and crossed/invalid-book rejection.
  - Product-scoped position reads, including Delta's documented single-object `/v2/positions?product_id=...` response, validated against product identity and position shape.
  - Per-product leverage POST plus GET read-back confirmation before entry; the reachable legacy `set_leverage()` wrapper method now uses the same documented `/v2/products/{product_id}/orders/leverage` endpoint, exact metadata lookup, and read-back check rather than the obsolete `/v2/orders/leverage` route.
  - A staged market-entry → cancel/re-read remainder → exact fill/position confirmation → separate bracket placement → independently paginated protective-child verification lifecycle. It verifies one active reduce-only stop and target child for the exact product and direction. It does **not** report atomic protection. Bracket failure, incomplete/missing children, or uncertain submit/fill state retains `SUBMISSION_UNKNOWN`; it attempts a deterministic reduce-only market close when fill and position are known but requires reconciliation before releasing ownership.
  - Bounded complete account snapshot from product catalogue, wallet, margined positions, exact per-perpetual position reads, active orders, owned entry/close IDs, and protective child IDs. Unowned orders are surfaced; mixed settlement currencies, unsupported positions, incomplete pages, malformed identity, missing protection, or unresolved owned orders prevent a complete snapshot. Reconciliation is capped by `JARVIS_DELTA_MAX_RECONCILE_PERPETUALS` (default 100, capped at 250) and bounded page counts.
  - Identity-scoped reduce-only close requests, independently protected by all five execution opt-ins, mainnet-wrapper selection, and the kill switch; current product and signed position are re-read before submit.
- `jarvis_risk.py` supports quote-value conversion only with explicit contract-unit and quote/settlement metadata, and risk amounts now carry a currency. No implicit USD/USDT/INR conversion is made; inverse/coin-margined or unknown contract units are rejected. The multicoin coordinator rejects mixed-currency numeric aggregation.
- `jarvis_delta_execution.py` uses exact Delta product metadata, Delta bid/ask, exact settlement-currency collateral, explicit contract value, lot rules, and risk currency. For other-than-USDT quotes, it scales deterministic levels using the same-asset Delta/Binance price ratio only when the same Delta quote and settlement currency is explicitly policy-authorized; it does not claim an FX conversion. Where a tier-wide maximum leverage is not explicitly supplied, sizing uses 1x rather than treating a product default as a maximum.
- `jarvis_FIXED.py` discovery uses the complete product catalogue and instrument-aware metadata, not hard-coded BTC or ticker-suffix inference. It retains Binance spot analysis identity separately from the exact Delta product execution identity and mapping-policy ID. India/Upstox routing is left separate. New modes remain default-off.
- `MULTICOIN_DELTA_EXECUTION.md` now documents the actual staged/non-atomic workflow, stop-limit gap/non-fill risk, exact collateral/currency policy, bounded reconciliation, activation gates, and live-verification limits.
- New `tests/test_delta_broker_transport.py` mocks only `_request` and exercises the actual wrapper response parsers and order lifecycle. It also drives a non-BTC ETH signal through `build_delta_candidate`/`DeltaExecutionAdapter`/`PortfolioCoordinator`, actual wrapper entry and bracket calls, fill verification, monitoring, reduce-only close, and restart reconciliation.

## Documentation evidence and uncertainty

Public official Delta documentation was consulted at `https://docs.delta.exchange/` (production India REST base documented as `https://api.india.delta.exchange`). The implementation follows the documented product metadata fields, cursor pagination, wallet `asset_symbol`/`available_balance`, L2 book, exact product-position endpoint, per-product leverage endpoint, order/client ID endpoints, and separate `/v2/orders/bracket` semantics. Delta's documented position-margin view may lag the exact per-product endpoint; the snapshot checks both. The bracket example returns only a success acknowledgement, and it is a separate post-fill operation, not atomic entry-plus-exits. Its stop-limit order can trigger but fail to fill across a price gap.

Documentation is not evidence of the live account's current product universe, account tier/margin rules, credential permissions, rate limits, response consistency, client-ID deduplication semantics, exact position/order transitions, bracket activation latency, or current India contract multiplier/lot behavior. These must be validated against current authorized broker schemas and account semantics before operation. No private or public exchange endpoint was called by this task; transport tests are offline fixtures only.
